Restart-\/pairing test for track\+\_\+freqn. 

Verifies that state\+\_\+ntime\+\_\+lastrestart correctly reflects the most recent restart-\/cadence point at each history completion. Restart files have NO completion lag (confirmed with the feature owner\+: written complete, instantly, at their own indicated hour -- unlike history files, which have the familiar \texorpdfstring{$\sim$}{\string~}1-\/tick FMS lag) -- so lastrestart is driven directly here as "{}the most recent restart\+\_\+hours(\+:) entry reached  so far,"{} no fixture files needed for restarts themselves. Also confirmed with the feature owner\+: in mom\+\_\+cap.\+F90, restarts are written, then outputlog\+\_\+restart is called (updating the module-\/level lastrestart this test drives an equivalent of), then outputlog\+\_\+run -- all within the same tick, so a restart due on tick T is correctly reflected in that same tick\textquotesingle{}s history completions, never lagging by a tick the way history completion itself does.

Reuses setup\+\_\+case/handlefiles from \doxylink{namespaceoutputlog__test__helpers}{outputlog\+\_\+test\+\_\+helpers} (shared with test\+\_\+freqn) for all the real ESMF clock/alarm/cf\+\_\+n/state\+\_\+n setup and history-\/fixture handling -- this file adds ONLY the restart-\/cadence driving and the state\+\_\+ntime\+\_\+lastrestart verification on top.

Deliberately does NOT call or verify log\+\_\+restart\+\_\+fh\+: track\+\_\+freqn itself never calls it (that only happens in outputlog\+\_\+run, which this test doesn\textquotesingle{}t exercise -- see the accompanying discussion on why outputlog\+\_\+run is treated as an accepted, unplanned gap for now), so doing so here would only confirm log\+\_\+restart\+\_\+fh formats whatever we hand it correctly, not anything about track\+\_\+freqn\textquotesingle{}s own behavior.

Case 1 only (freq=6, start=6, restart\+\_\+freq=15, runhours=36) -- case 2 (freq=24, start=0, restart\+\_\+freq=15, runhours=50) still needs its own diagram confirmed before being added.
